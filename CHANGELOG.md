# Changelog

Running log of what's been requested and built for Virtual Mirror, most recent first.

## 2026-10-16

### Virm redesign: clearer navigation, a styling dashboard, and a saved try-on photo
The app is now branded **Virm** ("Your virtual mirror for personal styling") and reorganized so a first-time user can find every tool without help. Navigation has six labeled sections with icons — Home, My Closet, AI Stylist, Try On, Saved Looks, Profile — as a top bar on desktop and a bottom tab bar on phones, with the current section highlighted. Every main page now opens with a title, a one-line explanation, and one obvious primary action, plus helpful empty, loading, success, and error states.
- **Home** is a personal dashboard: a "Next:" suggestion based on what the person has done, a "Your Virtual Mirror" section (saved photo with Try On an Outfit / Change Photo, or "Start with your photo" onboarding), and My Closet, AI Stylist, Try On, and Saved Looks sections with previews.
- **My Closet**: category tabs (All Items, Tops, Bottoms, Dresses, Outerwear, Shoes, Accessories), color/season/occasion/layer filters and search, a consistent grid, an item view with visible Edit, Remove (confirmed), and Style actions, and an "added" confirmation offering Add Another Item or Start Styling. "Occasion" uses the existing formality field; no data was invented.
- **AI Stylist**: a guided four-step flow (occasion, preferences, clothes to use, Generate My Outfits) with loading boards; each result is a labeled outfit board with Try On, Save Look, and View Outfit Details. The stylist still uses the whole closet — choosing specific items isn't supported by the backend, so it isn't offered.
- **Saved try-on photo** (reverses the earlier "never store the photo" decision, at the owner's request): the person saves one full-body photo with an explicit "Save My Photo" step; it is stored under a private key in the uploads bucket (`User.selfieUrl`, no schema change), served only to its owner by `GET /api/me/photo` (`PUT` replaces, `DELETE` removes), and refused by the public `/uploads` route. Try-on requests without a photo use the saved one, so it is never re-uploaded. Old public selfies are still cleaned up.
- **Try On**: a new Try On page (saved photo + Choose Outfit from saved looks or all outfits). Pressing Try On anywhere opens that outfit and generates immediately; refreshing or going Back doesn't start another paid try-on. The result offers Save Look, Try Another Outfit, Change My Photo, and Back to Outfits.
- **Current look stays on**: a real try-on result is kept privately as the person's current look (`private/looks/<userId>` in the uploads bucket, outfit id in its metadata — no schema change; owner-only `GET`/`DELETE /api/me/look`). Home, Try On, Profile, and the try-on screen show it until the person tries another outfit, presses Take Off Look, or changes/removes their photo. Opening Try On for the outfit already being worn shows it without generating again (Generate Again is available); new try-ons still start from the original photo.
- **Saved Looks** uses the same outfit boards with Try On, Remove from Saved, and View Look, and an empty state that points to Create an Outfit. **Outfit details** gets a breadcrumb back to AI Stylist or Saved Looks, its Try On / Save Look actions at the top, and a layout that works on phones. **Profile** shows account stats and manages the saved photo.
- Fix: vinext treats every multipart POST like a Server Action and capped it at 1MB, so Add Clothes and larger closet uploads failed with "Payload Too Large". `experimental.serverActions.bodySizeLimit` is now 25MB (each route keeps its own per-photo limit), and the Add Clothes dialog shows a readable message if an upload is rejected.
- Verified end to end on the local demo: add clothes → confirmation → Start Styling → generate dinner outfits → one-click Try On (≈6s, saved photo) → Save Look → Saved Looks → Try On another look (≈7s, same photo); all main pages fit a 375px phone with no horizontal scroll.

## 2026-10-15

### Try It On: real AI try-on with Black Forest Labs (FLUX VTO v2)
Try It On now produces a real AI image using Black Forest Labs' own FLUX virtual try-on API (`vto-v2`, called directly at api.bfl.ai) instead of the labeled prototype. New provider `lib/tryOn/providers/bflFluxVto.ts`, selected with `TRYON_PROVIDER=bfl-flux-vto` and keyed by the `BFL_API_KEY` secret (both now in `cloudflare.config.ts`). Following BFL's guidance, the browser lays every piece of the outfit out on one white sheet (`garmentSheet`, about 1 megapixel) and the whole look is dressed in a single call, so one try-on costs one generation and shoes and accessories appear too; the prompt lists the pieces innermost first with layering wording (inner top, layered over, worn open as the outer layer). If no sheet arrives it falls back to one call per piece. The job is submitted, polled at the returned regional URL, and the signed result (valid 10 minutes) is downloaded immediately and returned inline; nothing is stored. Errors map to plain messages (credits used up, key rejected, busy, photo declined by moderation), and the existing 10-per-hour per-user cap still applies. The fal.ai provider is left in place but no longer selected. Verified locally end to end against the real BFL service (a 5-piece outfit in one call, about 9 seconds).

## 2026-10-07

### Try It On: full experience, with a replaceable AI provider
Rebuilt the Try It On page as a complete flow while keeping the actual AI try-on swappable. From an outfit, the person adds a photo of themselves either with "Take a Photo" (the browser only asks for camera permission after that click, with a live preview, Capture, Retake, and "Use this photo"; if the camera is blocked or missing there is a clear message and uploading stays available) or "Upload a Photo" (any browser-readable image, with guidance to use a clear full-body photo). The page shows the real outfit being tried on, grouped by layer (outer, mid, base, bottom, shoes, accessories) with nothing invented, a "Change outfit" link back to Outfit Detail, and a primary "Try This Outfit On" button that shows the existing branded loading screen. The result has Save Look, Try Another Outfit, and Back to Outfit. The backend is now a small provider layer (`lib/tryOn`: a `TryOnProvider` interface, a registry chosen by the `TRYON_PROVIDER` setting, and a mock default), so a real service can be added by implementing one interface with no frontend or route changes. Because no real AI is connected, the result is clearly labeled as a prototype (a "Prototype preview" badge and a plain-language note) and shows the person's photo next to the outfit pieces, not a fake image of them wearing it. Privacy: the photo is downscaled in the browser, sent with the request, held in memory for that one call, and never stored; verified that storage and the database are unchanged after a try-on. The old save-a-photo behavior is gone: the save-photo endpoint was deleted, and photos the previous version had stored are removed automatically, once per person, the next time their account loads (their file is deleted from storage and the reference cleared; a file also used by a closet item is never touched). The camera capture is cropped to the same 3:4 frame as the preview, kept in true (un-mirrored) orientation, and Capture stays disabled until the camera is actually ready. No database schema changes (the now-unused photo column is left in place). Mobile-first pass: on phones the camera frame is sized to the screen and the Capture / Use this photo / Try This Outfit On / Save Look actions are pinned to the bottom edge above the home indicator (no scrolling to reach them), every tap target is at least 44px, and the layout was checked down to a 320px-wide phone and in landscape. The confirmed photo is now kept in memory for the Try It On session, so changing outfits (Outfit Detail, Saved Looks, AI Stylist) does not require taking it again; it is never saved to the account or to browser storage, and is discarded on logout, reload, choosing a different photo, or after 30 minutes idle. If the camera is taken away mid-capture (a call, an app switch) the page falls back to the choices with a clear message. FLUX virtual try-on provider added behind the same swap-in slot (`TRYON_PROVIDER=fal-flux-vto`, FLUX VTO hosted on fal.ai, key in `FAL_KEY`; the default stays the labeled prototype, so nothing changes until it is switched on). Because the model dresses one garment per call, a layered outfit is built one piece at a time, innermost first (bottom, base layer, mid layer, outer layer, with a dress first), feeding each result into the next call, with prompts that describe the layering (for example the cardigan worn over the shirt that is already on). Shoes and accessories are not rendered by this model, so the result says which pieces are not shown. The photo and garments are sent inline with fal's sync mode on (nothing uploaded, output kept out of its request history), failures map to plain messages (key missing, credits used up, busy), and a per-user cap of 10 try-ons per hour protects the credits. Tested end to end against a local stand-in for the service (call order, chaining, payloads, error paths); not yet tested against the real service. It is off by default and needs no Cloudflare change to stay off; to switch it on, add `TRYON_PROVIDER: bindings.text("fal-flux-vto")` and `FAL_KEY: bindings.secret()` to the env block in `cloudflare.config.ts` after adding the `FAL_KEY` secret to the Worker (see `.env.example`).

## 2026-10-02

### Dev account button (local only)
The login page has a "Continue with dev account" button (from the Figma login design) that signs in as the demo account with no password, so local changes are quick to check. It is served only when `NODE_ENV` is not production; the `/api/auth/dev-login` route returns 404 in production, so the live site has no passwordless login.

### Auth state and loading-screen behavior
Auth was being figured out separately by the nav and by every page, so logging out could leave the previous user's page visible, the branded loading screen flashed on ordinary page changes, and the public home still fetched closet/outfit data while signed out. Added one `AuthProvider` that owns three states: loading (branded screen), signed out (public intro or login only), and signed in (the app). The branded loading screen now shows only while auth is being resolved (first load or refresh) and once right after login; it no longer appears when moving between pages, and logout skips it and goes straight to the intro. Logout clears the user and remounts the whole app, so one user's closet, outfits, and profile can't carry over to the next. Signed-out visits to `/closet`, `/outfits`, `/outfits/saved`, `/profile`, or a try-on URL redirect to the login page. The login page now follows the Figma login design (split layout, "Welcome back." / "Begin with your closet."); the Figma's non-functional "Remember me", "Forgot password", and dev-account controls were left out. One small dev-only change in `lib/auth.ts`: local development auto-signs in a demo user, which silently undid every logout, so an explicit logout now sticks locally (production is unchanged). Removed the four route-level `loading.tsx` files and the artificial 500ms page-load delay. Verified in the browser: first visit, login, page-to-page navigation (no loader), logout, switching users with no leftover data, direct URLs while signed out, and refresh both signed in and signed out.

### Visual art-direction pass (no feature changes)
A separate pass focused purely on craft, on top of the now-solid Figma-structural foundation above — no backend, database, auth, AI logic, routes, or layering logic touched. Extracted the outfit "card" (the bordered tile with the editorial look-breakdown inside) into one shared `OutfitCard` component, since the AI Stylist results grid, Saved Looks grid, and Home's outfit showcase were each hand-copying the same markup — now they can't drift apart. Simplified that card itself: dropped the gradient background and box-shadow it had picked up, so it's a flat bordered tile with a soft lift-on-hover instead, to read as "four curated looks" rather than decorated boxes. Added a slow ambient drift animation to the existing `HeroBlob` accent (previously static) and used it on the Home hero and signed-in dashboard, tuned down in size/opacity after an in-browser check showed it muddying the stats row text. Added a shared `.btn-tactile` press-feedback convention (slight lift on hover, slight press on click) to every primary button across Home, Closet, AI Stylist, Saved Looks, Outfit Detail, Try It On, and Profile. Strengthened typographic hierarchy (bigger, clamp-sized headings) and widened whitespace on every page. Closet's sidebar lost its box/line treatment so it reads as quiet filter text rather than competing with the clothing photos, which also got more breathing room and a hover lift. Outfit Detail's "Change one item" control lost its boxed panel in favor of a plain labeled control, keeping the outfit itself as the visual centerpiece. Verified every changed page in-browser (not just `tsc`/`lint`) after each change, including generating a fresh outfit end-to-end to confirm the new card renders correctly.

### Full Figma-to-website reproduction pass
The site had drifted into its own interpretation of the Figma design rather than reproducing it. Found a reliable way to get the *exact* source instead of guessing from screenshots: Figma Make projects have a "Download code" option that exports the real `App.tsx`/`index.css`, which was read directly for every color, font, spacing, and component value used from here on. Rebuilt the whole frontend against that source: DM Sans + Instrument Serif typography, the real cool-chrome palette, sharp 5px-radius buttons instead of pill shapes, the Closet sidebar's full filter set (category, layering role, and color, plus the sidebar note box, all matching real values), and the Outfit Detail page's exact two-column ratio and title size. No backend, database, auth, or AI logic touched — purely layout, styling, and markup.

### AI Stylist, Saved Looks, and Profile as real pages
The Figma design turned out to have a 5-item nav (Home / My Closet / AI Stylist / Saved Looks / Profile) where this app only had two pages (Closet, Outfits). Split `/outfits` into a dedicated **AI Stylist** page (chip-based occasion/style selection, temperature + conditions weather controls, "Style Me") showing just the current session's results, a new **Saved Looks** page (`/outfits/saved`, favorites only, its own empty state) and a new **Profile** page (real stats — closet count, saved-looks count — avatar initials from the user's email, logout). No new database fields: Profile intentionally shows only data that already exists rather than adding editable fields with nowhere to persist to.

### Loading screens, toasts, and empty states
Added a branded full-screen loading state ("Melt": drifting, merging liquid-chrome blobs behind the "Virtual Mirror" wordmark — picked from 4 animated options after a side-by-side comparison) wired into every real data fetch across Home, Closet, Outfit Detail, Saved Looks, and Try It On. Discovered local data loads so fast the loading screen was flashing invisibly after the first page load, so added a shared `afterMinDelay` helper that holds it open for at least 500ms regardless of how fast the fetch actually resolves. Added a toast/confirmation system (bottom-right, auto-dismiss) firing on real actions — item added to closet, outfit saved/unsaved, item swapped. Added a proper "zero items at all" empty state to Closet, distinct from the "no items match this filter" state.

### Home page: a real intro before login, real tools after
Split the home page in two. Signed out, it's a pure introduction — headline, "How Virtual Mirror Works," a sample-closet teaser, and Log In/Create Account — with no real user data fetched or shown. Signed in, it becomes an actual dashboard: a "Hi, {name}" greeting, real stats, four quick-launch cards into the actual tools, a strip of the user's real closet photos, and the outfits showcase. Also found and fixed the nav itself showing My Closet/AI Stylist/Saved Looks/Profile links even while signed out — matching the real Figma source, those links (and the mobile menu) now only render once a user is actually signed in.

## 2026-09-29

### Outfit layering system
Outfits were a flat list of items with no concept of what goes under a jacket. Added a `layeringRole` (base_layer, mid_layer, outer_layer, bottom, one_piece, shoes, accessory) and `warmth` level to every closet item, independent of its category. The AI Stylist now decides which layers an outfit actually needs from weather/occasion/style *before* picking items — no forced mid or outer layer in warm weather, both added in cold weather, never a base layer or bottom under a dress unless asked. The outfit detail page now shows sectioned layer cards (outer → mid → base → bottom → shoes → accessories) instead of a flat grid, "Swap item" only offers same-layer replacements, and Try It On receives the full layered outfit instead of a flat item list. Verified against every scenario in the spec (warm/cool/cold weather, dress + jacket, hoodie + jacket stacking, and confirming the AI never invents an item — e.g. recommending a hoodie the user doesn't own).

### Multi-item clothing detection ("Add Clothes")
Previously required one photo per clothing item. Added a new "Add Clothes" flow: upload one photo of several items laid out separately (a flat lay), Claude's vision API detects each distinct piece with a bounding box, and a review step shows the photo with numbered boxes over each detected region plus an editable card per item (cropped preview, category, layering role, color, material, formality, season). Items can be edited, removed, or added manually before confirming. Nothing touches the closet until "Add to My Closet" — each confirmed item becomes its own closet entry with its own real cropped image, immediately usable by the outfit generator. Falls back to a clearly-labeled mock detector in demo mode (no API key).

### First-time-user QA pass
Walked through the full app as a genuine new user (signup → upload → generate → save → try-on → refresh → mobile) watching for broken buttons, console errors, bad state, and responsive issues. Found and fixed: a stuck-loading spinner when a closet/outfit fetch failed (no error handling on the client, so a transient server error froze the page forever instead of showing a retry option), the outfit detail page misreporting a transient server error as "outfit not found," and the Upload button being clickable while signed out with a cryptic "Not signed in" error instead of guiding to login. Added a D1 retry helper for the intermittent write-lock-contention 500s that caused the freeze in the first place.

### Strict MVP audit against the original spec
Audited all 17 requirements from the original product spec against the actual running code and live site (not just "does a screen exist"). Found and fixed the 5 highest-impact issues: no API route caught AI/storage failures (raw 500s with empty, unparseable bodies), a batch photo upload where one bad file discarded the whole batch, deleting a closet item could leave a "ghost" outfit with zero items but a full rationale for clothes that no longer existed, the "outfits use only your closet" rule was enforced by prompt text alone with no server-side check, and the nav bar overflowed off-screen on mobile.

### Outfit generation bugs + sample closet visuals
Fixed two production bugs blocking outfit generation entirely: Claude's structured-output API rejects `minItems`/`maxItems` values other than 0/1 on arrays (the schema had `minItems: 3`), and the response parser assumed the first content block was always text when Claude sometimes emits a `thinking` block first. Also replaced the 6 sample-closet placeholder images, which were flat colored rectangles, with actual garment-silhouette icons.
